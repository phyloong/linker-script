# AGENTS.md

This file provides guidance to CodeBuddy Code when working with code in this repository.

## Project

`linker-script` is a VS Code extension (publisher `amapleaf`, v0.2.0) that adds completion/snippets and hover documentation for GNU linker script (`.lds` and `.ld`) keywords, contributes the `linker-script` language with a TextMate grammar, and no longer touches `plaintext` documents. It is a single-purpose, very small codebase: eight source files plus a small test tree.

## Commands

- `npm run compile` — `tsc --noEmit` (type check) followed by `node esbuild.js` (bundle). The bundle is `dist/extension.js`, which is what `main` points at.
- `npm run typecheck` — type check only (`tsc --noEmit`); produces no output files.
- `npm run bundle` — esbuild only; writes `dist/extension.js` plus the compiled test bundles under `dist/test/`.
- `npm run watch` — one type check, then `node esbuild.js --watch`; this is the `preLaunchTask` for the launch configurations in `.vscode/launch.json`. The task's custom problem matcher keys off esbuild's `[watch] build started/finished` lines.
- `npm run lint` — ESLint flat config (`eslint.config.mjs`) with type-aware `typescript-eslint` rules.
- `npm test` — `npm run compile`, then `npm run test:unit`, then `npm run test:grammar`, then `npm run test:extension`.
- `npm run test:unit` — plain Mocha (TDD UI) over `dist/test/unit/**/*.test.js`. No VS Code download, no extension host; run `npm run bundle` first if `dist/` is stale.
- `npm run test:grammar` — `vscode-tmgrammar-test "test/grammar/**/*.ld"`, which reads `contributes.grammars` from `package.json` and checks the inline `^` assertions in each fixture against the real tokenizer, then `node scripts/check-grammar-fixtures.mjs`, which fails when any non-space character of a fixture source line is left outside an assertion (the guard that makes a silently dropped scope break `npm test`) and rejects a `#include` with no repository entry. Run a single fixture with `npx vscode-tmgrammar-test "test/grammar/memory.ld"`.
- `npm run test:extension` — `vscode-test` with `.vscode-test.mjs`, which targets `dist/**/*.test.js` (so the pure-Node suites also run a second time inside the host) and downloads VS Code 1.74.0 into `.vscode-test/` on first run.
- Run a single unit test: `npx mocha --ui tdd dist/test/unit/placeholder.test.js` (or change the glob).
- Run a single extension-host test: `npx vscode-test --grep "Extension Tests"` — Mocha's filters are passed through to the test run — or use `suite.only` / `test.only` in `src/test/extension.test.ts`.
- `npm run package` — produces `linker-script-0.2.0.vsix` via the local `@vscode/vsce` binary (`vscode:prepublish` runs `npm run compile` first). `.vscodeignore` ships the compiled `dist/extension.js` together with `language-configuration.json`, `syntaxes/linker-script.tmLanguage.json`, `img/Script.png` (the icon), README, CHANGELOG and LICENSE; `out/`, `src/`, `node_modules/`, source maps, `dist/test/`, `test/`, `scripts/`, the CI workflow, `package-lock.json`, and the repo's agent/tooling directories are excluded. `npx vsce ls` shows the exact file list.
- CI: `.github/workflows/ci.yml` runs type check, bundle, unit tests, grammar tests, extension-host tests (under `xvfb-run`), `vsce package` and `vsce ls` on every push and pull request. `.github/workflows/release.yml` repeats that chain on a `v*` tag or on a manual dispatch, checks a tag push against `package.json` (a manual run from a branch publishes the `package.json` version), prints the artifact and its checksum, then publishes with `vsce publish --oidc` (trusted publishing, `id-token: write`); if the optional `VSCE_PAT` repository secret is set, the same step publishes with that scoped token instead. Neither workflow runs inside this sandbox, so a local run of the same commands is the equivalent evidence.
- Release status: `release.yml` publishes with `npx vsce publish --packagePath ./*.vsix --oidc`, falling back to the `VSCE_PAT` token when that secret exists. Version 0.2.0 itself was published from the web UI, because the tag-triggered run failed at the OIDC exchange with 401 (the publisher had no federated credential then). On 2026-11-05 a manual dispatch did verify trusted publishing: the OIDC token exchange succeeded and `vsce` then stopped at `amapleaf.linker-script v0.2.0 already exists`, so nothing was published. Whether a tag push has since completed that exchange is not recorded in this repository.
- Debugging: F5 with the **Extension** launch config opens a second VS Code window with this extension loaded. Open a file named `*.lds` or `*.ld` there to test completions and hover.

## Architecture

- `package.json` — `contributes.languages` declares the language id **`linker-script`** with the `.lds` and `.ld` extensions, the aliases, and `configuration: ./language-configuration.json`. `contributes.grammars` maps `linker-script` to `syntaxes/linker-script.tmLanguage.json` with root scope `source.linker-script`. `activationEvents` is `['onLanguage:ld']`: activation for `linker-script` is implicit at `engines.vscode ^1.74.0` (VS Code turns a contributed language into an activation event at runtime; the packaged manifest still lists only `onLanguage:ld`, and `src/test/extension.test.ts` asserts that showing a `linker-script` document with no workspace activates the extension), and `onLanguage:ld` is declared because `ld` is contributed by other extensions, not by this one. `description`, `categories` (`Programming Languages`, `Snippets`), `keywords` and `capabilities` describe the shipped behavior: every feature only reads the open document, so `untrustedWorkspaces` and `virtualWorkspaces` are declared fully supported and the extension has no runtime dependencies.
- `src/extension.ts` — `activate()` calls `registerCompletionProviders(context)` and `registerHoverProviders(context)`; each registers one provider per id in `SUPPORTED_LANGUAGE_IDS` and pushes one disposable per registration. `plaintext` is deliberately not registered. Both registration functions take an optional registrar parameter (default: `vscode.languages.registerCompletionItemProvider` / `vscode.languages.registerHoverProvider`) so the extension-host test can record which selectors are registered.
- `src/languages.ts` — exports `SUPPORTED_LANGUAGE_IDS` (`linker-script`, `ld`). It imports nothing, so plain-Node unit tests can assert the list without the `vscode` module; `src/test/unit/language.test.ts` also asserts the manifest fields and the `wordPattern` regex.
- `syntaxes/linker-script.tmLanguage.json` — the TextMate grammar, root scope `source.linker-script`. It is organized by block: `#section-items` is the shared include for statements legal in `SECTIONS`, in an output section body, and inside a parenthesised input group, while `#sections-body`, `#section-header`, `#overlay`/`#overlay-section`, `#memory-body`, `#phdrs-body` and `#version-body` supply the constructs that only exist while their block is open. A block keyword owns its brace: the `SECTIONS`, `MEMORY`, `PHDRS` and `VERSION` entries take `KEYWORD` plus an optional `{`, so a brace on the next line still belongs to the block (`OVERLAY` starts its region at the keyword without consuming the brace), and a section body is a region (`.name [(type)] : {`) rather than a bare `{`, which is what keeps the closing braces balanced. See "Syntax highlighting" below for the scope vocabulary.
- `test/grammar/` — `vscode-tmgrammar-test` fixtures, one file per construct family, with the expected scopes annotated inline. `scripts/check-grammar-fixtures.mjs` verifies that every non-space character of a fixture line sits inside an assertion, so the suite fails when a scope disappears instead of a token quietly going unstyled.
- `language-configuration.json` — editor configuration for the language: `/* */` as the only comment token (so toggle-line-comment inserts a block comment), bracket pairs, block-comment `#region` folding markers, and a `wordPattern` that keeps `SORT_BY_NAME` and `.text.foo` as single words.
- `src/keywords/registry.ts` — the single source of truth for keyword data: `KEYWORDS` is an array of `{ id, kind, snippet, summary, example, signature?, scopes }` entries, where `kind` is one of `block`, `command`, `function`, `field`, `keyword` and `scopes` is a list drawn from `top | sections | section-body | memory | phdrs | version | overlay`. `keywordsForScope(scope)` returns the entries whose `scopes` list names that scope. The `version` scope holds three lower-case version-script commands (`global`, `local` and `extern`), which are separate entries from the upper-case top-level `EXTERN(symbol)` command. `summary` is the only copy of the description (completion and hover both read it) and `example` is the hover-only usage sample; the optional `signature` overrides the form derived from `snippet`. `SUMMARY_MAX_LENGTH`, `EXAMPLE_MAX_LENGTH` and `EXAMPLE_MAX_LINES` state the content caps. The module imports nothing from `vscode`, so plain-Node tests cover it; adding a keyword is one array entry, and no second copy of the data exists anywhere.
- `src/keywords/scanner.ts` — the scope scanner behind the filtering. `scanScopes(text, cursorOffset)` makes one pass over the text before the cursor, tracking normal/comment/string state and a brace stack labelled by block keyword (`SECTIONS`, `MEMORY`, `PHDRS`, `VERSION`, `OVERLAY`); an unlabelled brace inside `SECTIONS` or `OVERLAY` pushes `section-body`. It returns the innermost scope plus `path` (see `formatPath`) and flags `uncertain` with a `reason` on a stray `}`, an unterminated comment, or an `INCLUDE` before the cursor; `inCommentOrString` reports a cursor inside a comment or string. It is `vscode`-free as well.
- `src/hover/HoverProvider.ts` — a thin renderer like `Completion.ts`. It asks `document.getWordRangeAtPosition(position, keywordWordPattern())` for the token under the cursor, looks it up with `keywordById`, and returns undefined for a word the registry does not know; otherwise it builds a `MarkdownString` from the derived signature (fenced block), the `summary`, and the `example` (fenced block). `isTrusted` stays false because no command links are rendered. There is no keyword data in this file and no scope filtering: hover answers wherever the word appears, in comments and strings included.
- `src/keywords/signature.ts` — `deriveSignature(snippet)` strips `${n:default}` to the default (a bare `${n}` disappears) and collapses a multi-line brace body to `{ ... }`, so `ALIGN(${1:expression})` reads as `ALIGN(expression)` and the `SECTIONS` snippet as `SECTIONS { ... }`; `signatureOf(entry)` prefers the optional `signature` override. It is `vscode`-free, so `src/test/unit/signature.test.ts` covers it.
- `src/keywords/lookup.ts` — `keywordById(id)` is an exact-id map lookup (no prefix or case-insensitive fallback), and `keywordWordPattern()` builds a fresh global regex from the registry ids, longest first, sandwiched in `(?<![A-Za-z0-9_$])…(?![A-Za-z0-9_$])` plus a bare `!` branch (that keyword is a prefix, as in `(!rx)`). It is `vscode`-free as well.
- `src/Completion.ts` — a thin renderer. `CompletionProvider.provideCompletionItems` scans the document at the cursor, then maps registry entries to `vscode.CompletionItem`s with the category-to-kind table (`block` → `Struct`, `command` → `Method`, `function` → `Function`, `field` → `Field`, `keyword` → `Keyword`), a `SnippetString` from the entry, and `entry.summary` as `item.documentation` (the same string hover shows). An uncertain scan returns every registry entry; a cursor inside a comment or string returns none. There is no keyword data in this file and no prefix matching or trigger-character logic.
- `README.md` / `CHANGELOG.md` — both ship inside the `.vsix` and must stay true of the built extension. The README is ordered description, features, a complete example script, compatibility/coexistence (naming `squarewave.linker-script-syntax` and the file-association rule), requirements, limitations; the 0.2.0 changelog entry leads with the breaking changes (language id, removal of `plaintext` completion, minimum VS Code 1.74.0).
- `esbuild.js` — two build configs: the extension bundle (`src/extension.ts` → `dist/extension.js`, `platform: node`, `format: cjs`, `external: ['vscode']`) and the test bundle (`src/test/**` → `dist/test/**`, same settings). `vscode` is the only runtime require in the output.
- `src/test/` — `src/test/extension.test.ts` holds the extension-host suite, which drives real completion requests to prove scope filtering, the uncertain fallback, the empty comment/string result, and the kind mapping, and real `vscode.executeHoverProvider` requests to prove the ALIGN, MEMORY, PROVIDE and ASSERT tooltips, the fenced-block rendering, the silence over `__stack_top`, `.text` and plain-text documents, and the rejection of `ALIGN` inside `MY_ALIGN` and `ALIGNMENT`; `src/test/unit/` holds pure-Node suites (`language.test.ts` for the manifest and editor configuration, `keywords.test.ts` for registry coverage, invariants, scope filtering, exact snippets and the summary/example caps, `scanner.test.ts` for nesting, section bodies, every uncertainty condition and a several-thousand-line smoke run, `signature.test.ts` for signature derivation, `lookup.test.ts` for exact-id lookup and the word pattern); both use the Mocha **TDD** UI (`suite`/`test`, not `describe`/`it`), configured through `.vscode-test.mjs` (extension host) and the `test:unit` script (plain Node). The old `src/test/index.ts` runner is gone — `@vscode/test-cli` supplies the runner.

## Syntax highlighting

- Root scope is `source.linker-script`, deliberately not `source.ld`: another extension registers a grammar with that root for the same extensions, and two grammars claiming one root conflict. Every leaf scope ends in `.ld` (`keyword.control.command.ld`), which is the compatibility contract a theme or a `textMateRules` override targets; `source.linker-script` itself is the only exception.
- Leaf scopes, by family:
  - comments and strings: `comment.block.ld`, `punctuation.definition.comment.ld`, `string.quoted.double.ld`, `string.quoted.single.ld`, `punctuation.definition.string.begin.ld`, `punctuation.definition.string.end.ld`, `constant.character.escape.ld`
  - literals: `constant.numeric.ld` (decimal, `0x` hex, leading-zero octal, and the `K`/`M` suffix inside the same token)
  - commands and blocks: `keyword.control.command.ld`, `keyword.control.block.ld`, `keyword.other.ld` (`NOLOAD`, `DSECT`, `COPY`, `INFO`, `CONSTRUCTORS`, `CREATE_OBJECT_SYMBOLS`, `FORCE_COMMON_ALLOCATION`), `support.function.ld` (`ALIGN`, `SIZEOF`, `ADDR`, …)
  - sections: `entity.name.section.ld` (output section name, `/DISCARD/`, overlay section), `entity.name.section.input.ld` (input pattern such as `.text*`), `variable.other.location-counter.ld`, `variable.other.symbol.ld` (assignment target)
  - regions: `keyword.operator.region-marker.ld` (`>`, `AT>`, `AT(`), `entity.name.tag.region.ld`, `keyword.other.region-field.ld` (`ORIGIN`/`LENGTH` and their short spellings), `meta.attributes.region.ld` wrapping `keyword.other.region-attribute.ld`
  - program headers: `entity.name.tag.phdr.ld`, `support.type.program-header.ld` (`PT_*`), `keyword.other.phdr-flag.ld` (`FILEHDR`, `PHDRS`)
  - versions: `entity.name.tag.version.ld` (version node), `keyword.other.version.ld` (`global`/`local`/`extern`), `entity.name.symbol.ld`
  - operators and punctuation: `keyword.operator.exclusion.ld` (`!`), `keyword.operator.wildcard.ld` (`*`), `keyword.operator.assignment.ld`, `keyword.operator.comparison.ld`, `keyword.operator.ld`, `punctuation.section.block.begin.ld`, `punctuation.section.block.end.ld`, `punctuation.section.parens.begin.ld`, `punctuation.section.parens.end.ld`, `punctuation.separator.colon.ld`, `punctuation.separator.comma.ld`, `punctuation.terminator.statement.ld`
- A new grammar construct gets a scope from an existing family before it gets a new name, and the name still ends in `.ld`. The grammar and `src/keywords/registry.ts` are separate data: the registry decides what completion and hover offer, the grammar what is colored, and a new keyword needs both. `npm run test:grammar` is the check that the fixtures still describe the grammar.
- Regex discipline: patterns are anchored on `\b`/lookbehind rather than left open, and no pattern nests a quantifier over a class that overlaps itself, so a malformed line cannot backtrack. Fixtures under `test/grammar/malformed-*.ld` keep that honest: an unterminated comment runs to the end of the file, a stray `}` is colored as punctuation, and a section body left open at the end of the file ends there instead of stalling.

## Hover documentation

- Hovering a registered keyword shows three things: the signature in a fenced code block, the one-sentence `summary`, and the `example` in a second fenced block. The content is a `MarkdownString` with `isTrusted` left false, because only code blocks and prose are rendered.
- The signature is derived from `snippet`, not hand-written: `${n:default}` becomes the default, a bare `${n}` disappears, and a brace body spanning lines collapses to `{ ... }` (`ALIGN(${1:expression})` reads `ALIGN(expression)`, the `SECTIONS` snippet reads `SECTIONS { ... }`). An entry may set `signature` to replace the derived form; none currently do.
- The word under the cursor comes from `getWordRangeAtPosition` with `keywordWordPattern()`, a global regex built from the registry ids (longest first) and bounded by `(?<![A-Za-z0-9_$])` / `(?![A-Za-z0-9_$])`, plus a bare `!` branch because that keyword is a prefix in `(!rx)`. A range is then resolved with `keywordById`, which answers exact ids only — so `ALIGN` in `ALIGN(0x10)` hovers whole, while `__stack_top`, `.text`, `ALIGNMENT` and `MY_ALIGN` produce nothing.
- Hover is registered for exactly `SUPPORTED_LANGUAGE_IDS` (`linker-script`, `ld`), so a plain-text document never receives one. Hover does not filter by `scopes`: a registered word is answered wherever it appears, including comments and strings.

## Documentation provenance

- Every `summary` and `example` in `src/keywords/registry.ts` must be written for this project. Do not copy or closely reword passages from the GNU ld manual: it is distributed under the GNU Free Documentation License, which is incompatible with this project's Apache-2.0 license, so such text cannot ship. Describe the same behavior in your own words and build examples from scratch.
- Keep a summary to one sentence (at most `SUMMARY_MAX_LENGTH` = 160 characters, ending in a full stop, no internal sentence break) and an example to a few lines (at most `EXAMPLE_MAX_LENGTH` = 200 characters and `EXAMPLE_MAX_LINES` = 4 lines, spaces instead of tabs). `src/test/unit/keywords.test.ts` enforces presence and the caps, so an entry without both fields fails the unit suite.
- The prose exists once. `summary` is what completion puts in `CompletionItem.documentation` and what hover shows under the signature; never add a second description field with the same text.
- A keyword legal in several places must name every placement in its `scopes` list inside the summary (a unit test checks every entry whose `scopes` list holds more than one placement), because hover itself is scope-agnostic.

Build constraints: `tsconfig.json` sets `strict` and `noUnusedLocals` with `rootDir: src` and `noEmit: true`, so any new source file must live under `src/` and every local must be used, or `npm run compile` fails at the type-check step before anything is written to `dist/`. The toolchain is TypeScript 5.9 (the 7.x line is blocked by `typescript-eslint`'s `<6.1.0` peer range), `@types/node` 16, and `engines.vscode ^1.74.0` with `@types/vscode ~1.74.0` pinned to the same floor — avoid TS or VS Code APIs those versions do not provide. The developer tooling (`@vscode/test-cli`/`@vscode/test-electron`, `@vscode/vsce`, `mocha`, `eslint`) needs Node >= 22.13 on the developer machine; that is a build-time requirement only and does not raise `engines.vscode`, since the extension host still runs the Node 16 bundled with VS Code 1.74.

## OpenSpec workflow

This repo is managed with OpenSpec (`schema: spec-driven` in `openspec/config.yaml`). All specs, proposal, design, and task artifacts **must be written in English**; keep OpenSpec headings and SHALL/MUST keywords in English. Active changes live in `openspec/changes/` (completed ones under `openspec/changes/archive/`), and long-lived specs in `openspec/specs/`. OpenSpec ships its workflow as agent skills under `.agents/skills/openspec-*`, which is the only agent directory tracked here. Other agent tools keep their own copies of those instructions on the developer's machine and are gitignored (`.claude/`, `.codebuddy/`, `.opencode/`). Use the `opsx` workflow rather than editing `openspec/` files by hand.
